# Deploying "El Renad" to Render

Two services, one blueprint. The backend is a NestJS API; the frontend is a
Next.js app. They deploy as **separate Render web services on separate origins**
(unlike a single-VPS setup), so the cross-origin URLs must be wired up by hand
after the first deploy.

---

## 1. Prepare MongoDB Atlas

The app connects to cluster `cluster0.95lwiab.mongodb.net`, database `school`.

1. Atlas → **Network Access** → add `0.0.0.0/0` (Allow access from anywhere).
   Render's free/standard plans have **no static outbound IP**, so an IP
   allowlist is not practical.
2. Atlas → **Database Access** → confirm user `nohoge1227_db_user` has
   `readWrite` on the `school` database (or `readWriteAnyDatabase`).
3. Connection string (used as `MONGODB_URI`):
   ```
   mongodb+srv://nohoge1227_db_user:<password>@cluster0.95lwiab.mongodb.net/school?retryWrites=true&w=majority
   ```

## 2. Create the services from the blueprint

1. Push this repo to `https://github.com/hazem-e99/school-fleet-v1.git`.
2. Render Dashboard → **New → Blueprint** → connect the GitHub repo.
3. Render reads `render.yaml` and proposes `elrenad-backend` + `elrenad-frontend`.
4. Click **Apply**. The first build will start; `sync: false` vars are still blank.

## 3. Fill in environment variables

### elrenad-backend
| Key | Value |
|---|---|
| `MONGODB_URI` | the Atlas string from step 1.3 |
| `CORS_ORIGIN` | the frontend URL once known, e.g. `https://elrenad-frontend-xxxx.onrender.com` |

`JWT_SECRET` is auto-generated by Render. `HOST=0.0.0.0`, `DB_NAME=school` come
from the blueprint. `PORT` is injected by Render. There is no email/SMS — auth
is phone + password, and there is no self-service password reset: an admin resets
a user's password from the Users page (`PUT /api/Users/:id/reset-password`).

### elrenad-frontend
| Key | Value |
|---|---|
| `NEXT_PUBLIC_APP_URL` | this frontend's own URL, e.g. `https://elrenad-frontend-xxxx.onrender.com` |
| `NEXT_PUBLIC_API_BASE_URL` | `https://elrenad-backend-xxxx.onrender.com/api` |
| `NEXT_PUBLIC_BACKEND_ORIGIN` | `https://elrenad-backend-xxxx.onrender.com` |
| `NEXT_PUBLIC_MAPBOX_ACCESS_TOKEN` | optional (maps) |

> **Order of operations**: after the first deploy each service gets its
> `onrender.com` URL. Put the backend URL into the three frontend
> `NEXT_PUBLIC_*` vars and the frontend URL into the backend `CORS_ORIGIN`, then:
> - **Manual Deploy → Clear build cache & deploy** the **frontend** (Next.js
>   inlines `NEXT_PUBLIC_*` at build time — a restart is not enough).
> - Restart/redeploy the **backend** to pick up `CORS_ORIGIN`.

## 4. Verify

- Backend health check: `GET https://elrenad-backend-xxxx.onrender.com/api/Settings/maintenance-mode`
  → `{"maintenanceMode":false}` (Render also pings this automatically).
- Frontend loads at its URL; browser tab shows **الريناد**.
- Log in with a seeded account (see step 5). No CORS errors in the console.
  Check the bus-tracking page for socket errors.

## 5. Seed the database (once)

Run against the Atlas connection string. Easiest is a Render one-off **Job**
(New → Job, same repo, `rootDir: backend`, command `npm run seed`, with the
same `MONGODB_URI` + `DB_NAME=school` env vars) — or the `elrenad-backend`
service **Shell** tab (`npm run seed`), or locally:
```bash
cd backend
MONGODB_URI="mongodb+srv://nohoge1227_db_user:<password>@cluster0.95lwiab.mongodb.net/school?retryWrites=true&w=majority" \
DB_NAME=school \
npm run seed
```
This creates collections + indexes, the default `settings` doc
(`systemName: "El Renad"`, indigo/sky colors), and demo data:
| role | login (phone) | password |
|---|---|---|
| Admin | `01000000001` | `Admin@123` |
| Guardian (parent) | `01000000005` / `01000000006` | `Parent@123` |
| Driver | `01000000002` | `Driver@123` |
| Conductor | `01000000003` | `Conductor@123` |
| Movement Manager | `01000000004` | `Manager@123` |

plus 4 children (linked to the two guardians), 6 schools, 6 pickup areas,
5 buses, 3 routes, 4 subscription plans.

To wipe and re-seed, run `RESET_CONFIRM=YES npm run reset-db` first (or
`node scripts/reset-db.js`), then `npm run seed`.

> **`mongodb+srv` note**: the SRV lookup needs a working DNS resolver. Render's
> is fine. If a local `npm run seed` hangs with `querySrv ECONNREFUSED`,
> preload a public resolver: `node -e "require('dns').setServers(['8.8.8.8'])" -r`
> is not a thing — instead put `require('dns').setServers(['8.8.8.8','1.1.1.1'])`
> in a small `dns-fix.js` and run `node -r ./dns-fix.js seed.js`.

## 6. Notes / caveats

- **Free plan** services spin down after ~15 min idle; the first request after
  idle takes ~30–60s. Fine for testing; upgrade for always-on.
- **Uploads**: profile pictures are stored in **MongoDB GridFS** (bucket
  `uploads`) in the same Atlas database, served by `GET /api/files/:id`. They
  survive redeploys — no Render Disk or `UPLOAD_DIR` needed.
- **Custom domain**: add it per service under **Settings → Custom Domains**, then
  update `NEXT_PUBLIC_APP_URL` / `NEXT_PUBLIC_API_BASE_URL` /
  `NEXT_PUBLIC_BACKEND_ORIGIN` / `CORS_ORIGIN` accordingly and rebuild the
  frontend.
